# Замечания к opens3-rebac

Находки, полученные при чтении кода сервиса авторизации в ходе работы над
детектором аномалий. Файл пополняется. Статус проверки указан честно: часть
находок получена чтением кода и требует подтверждения запуском.

Ссылки даны на пути внутри `/home/wexel/Data/Code/Projects/opens3-rebac`.

## 1. Права на бакет не распространяются на его объекты

**Важность: высокая. Статус: найдено чтением кода, требует подтверждения запуском.**

`services/authz/internal/repositories/neo4j/store.py`, метод `check`:

```cypher
MATCH (subj {id: $subject})-[:MEMBER_OF*0..]->(x)-[p:HAS_PERMISSION]->(res {id: $object})
WHERE p.level IN $allowed_levels
RETURN count(p) > 0 AS authorized
```

Запрос обходит цепочку членства в группах, но не обходит иерархию ресурсов:
`res` обязан быть ровно тем объектом, о котором спросили. Ребро `PARENT_OF`
в проверке не участвует нигде.

Следствие: право, выданное на `bucket:my-photos`, не даёт доступа к
`object:my-photos/cat.jpg`. Между тем `PARENT_OF` описано в контракте
`shared/api/authz/v1/authz.proto` именно как связь бакета с объектом,
создаваемая после `PutObject`, а иерархия вложенных контейнеров заявлена как
одна из причин выбора ReBAC вместо RBAC.

Ожидаемый вид проверки — дополнительный обход вверх по иерархии ресурсов:

```cypher
MATCH (subj {id: $subject})-[:MEMBER_OF*0..]->(x)-[p:HAS_PERMISSION]->(container)
MATCH (container)-[:PARENT_OF*0..]->(res {id: $object})
WHERE p.level IN $allowed_levels
RETURN count(p) > 0 AS authorized
```

**Проверка:** выдать `HAS_PERMISSION{read}` на бакет, создать `PARENT_OF` от
бакета к объекту, вызвать `Check(user, read, object)`. Ожидается `false` при
текущей реализации.

## 2. OWNER_OF невозможно создать через gRPC

**Важность: средняя. Статус: подтверждено чтением, расхождение однозначное.**

`shared/api/authz/v1/authz.proto` в комментарии к `WriteTuple` прямо описывает
сценарий:

> назначить владельца бакета при CreateBucket:
> `subject=user:<id>, relation=OWNER_OF, object=bucket:<name>`

Однако `enum Relation` в том же файле содержит только `RELATION_MEMBER_OF`,
`RELATION_HAS_PERMISSION` и `RELATION_PARENT_OF`. Значения `OWNER_OF` в нём нет.

Соответственно `_RELATION_TO_STR` в
`services/authz/entrypoints/server/servicer.py` его не содержит, и любой вызов
`WriteTuple` с намерением назначить владельца завершится
`INVALID_ARGUMENT: relation is required`.

При этом `OWNER_OF` живёт в `internal/repositories/neo4j/schema.py` и участвует
в `PERMISSION_RULES`, то есть в запасной ветке проверки прав. Получается
отношение, которое учитывается при авторизации, но которое штатным API
создать нельзя.

**Варианты исправления:** либо добавить `RELATION_OWNER_OF = 4` в proto, либо
убрать `OWNER_OF` из логики проверки и выражать владение через
`HAS_PERMISSION{admin}`. Второе проще и сокращает число сущностей, но первое
точнее отражает намерение.

## 3. Владение и членство не наследуются по иерархии ресурсов

**Важность: средняя. Статус: следствие находки 1.**

Запасная ветка `check` ищет только прямое ребро:

```cypher
MATCH (subject {id: $subject})-[rel]->(target {id: $object})
WHERE type(rel) IN $allowed_rels
```

Здесь нет ни обхода `MEMBER_OF`, ни обхода `PARENT_OF`. Поэтому владелец бакета
не является владельцем его объектов, а группа, помеченная как `OWNER_OF`, не
передаёт владение своим участникам. Для `VIEWER` и `OWNER_OF` это означает, что
они работают только в самом вырожденном случае.

## 4. Отсутствуют метки времени на узлах и рёбрах

**Важность: средняя для аудита, нулевая для авторизации. Статус: подтверждено.**

Запросы `MERGE` в `store.py` не проставляют ни `created_at`, ни `updated_at`.
По графу невозможно ответить на вопрос «когда это право было выдано», а значит
невозможен и ретроспективный аудит: журнал изменений существует только в Kafka
и живёт столько, сколько настроено хранение топика.

Это первая из двух правок, вносимых в рамках настоящей работы.

---

## 5. Не сохраняется инициатор изменения прав

**Важность: средняя. Статус: подтверждено.**

Ни `WriteTupleRequest`, ни `DeleteTupleRequest`, ни аудит-событие в
`internal/repositories/kafka/producer.py` не содержат того, кто выполнил
изменение. По графу и по журналу невозможно отличить право, выданное
администратором, от права, которое субъект выдал сам себе.

Это общее свойство Zanzibar-подобных систем, а не упущение конкретной
реализации, но именно оно ограничивает обнаружение эскалации привилегий.

Это вторая из двух правок, вносимых в рамках настоящей работы.

---

## 6. Операция записи отношения не авторизуется

**Важность: высокая с точки зрения безопасности. Статус: подтверждено. Вне объёма ВКР.**

`PermissionService.write_tuple` выполняет запись безусловно: проверки того,
вправе ли вызывающий выдать данное право, нет ни в сервисе авторизации, ни
где-либо ещё в цепочке. Любой, кто может обратиться к gRPC-порту, может выдать
себе `admin` на любой ресурс.

В классическом Zanzibar авторизация записи действительно возложена на
приложение, а не на движок, так что формально это не противоречит модели. Но в
текущем состоянии системы такого приложения нет: `services/gateway` пуст, и
порт сервиса авторизации в `docker-compose.yml` открыт напрямую.

Исправление требует правил делегирования и их проверки, что выходит за рамки
настоящей работы. Зафиксировано как направление развития.

## 7. Подстановка типа отношения в текст запроса Cypher

**Важность: низкая сейчас, потенциально высокая. Статус: подтверждено, но не эксплуатируется.**

`_write_plain_relation` и `delete_tuple` подставляют тип отношения в текст
запроса форматированием строки:

```python
query = """
MERGE (subject)-[rel:`%s`]->(object)
""" % (s_label, o_label, tuple_.relation)
```

Сейчас это безопасно: единственный путь снаружи проходит через `_RELATION_TO_STR`,
где строка берётся из фиксированного словаря по значению enum. Но защита держится
на вызывающем коде, а не на самом хранилище. Любой новый путь вызова — консьюмер
Kafka, служебный скрипт, тест с внешними данными — снимает её.

Обратные кавычки вокруг подстановки не спасают: имя отношения, содержащее
обратную кавычку, закрывает идентификатор.

**Исправление:** валидировать `tuple_.relation` по `RelationType` внутри
`Neo4jStore` перед построением запроса и отвергать всё остальное.

## 8. Неограниченная глубина обхода членства

**Важность: низкая. Статус: замечание по производительности.**

Шаблон `[:MEMBER_OF*0..]` не имеет верхней границы. Циклы Neo4j отсекает сам,
поскольку не повторяет рёбра в пути, но стоимость обхода на плотном графе групп
не ограничена ничем. Разумная граница — глубина вложенности групп, принятая в
системе, например `*0..5`.

## 9. Избыточная подсказка инвалидации кэша

**Важность: косметическая. Статус: подтверждено.**

`AuditProducer.send_tuple_event` публикует два шаблона инвалидации:

```python
f"auth_decision:{tuple_.subject}:*:{tuple_.object}",
f"auth_decision:*:*:{tuple_.object}",
```

Второй полностью поглощает первый. Достаточно второго.
