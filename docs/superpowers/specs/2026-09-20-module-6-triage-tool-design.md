# Модуль 6. Инструмент триажа: дизайн

Дата: 20.09.2026. Продолжение модуля 4, который построил сервис, объяснение и
страницу. Модуль 6 превращает страницу из списка в рабочий инструмент: появляется
состояние разбора, переживающее перезапуск, и действия аналитика над очередью.

## 1. Задача

Нынешний интерфейс показывает ранжированный список и карточку. Работать с ним
нельзя: разобранный случай остаётся в списке навсегда, повторяющееся законное
изменение — например, инженер по ИБ, выдающий себе права в ходе работ, — занимает
верх очереди при каждом обновлении, а следа от разбора не остаётся нигде.

Настоящая работа специалиста устроена иначе: он просматривает очередь, часть
случаев признаёт нормой, часть — требующими вмешательства, и в обоих случаях
решение должно быть зафиксировано. Инструмент обязан это поддерживать, иначе
ранжирование, каким бы точным оно ни было, не доходит до применения.

## 2. Границы

Модуль делает:

- журнал решений аналитика, переживающий перезапуск сервиса;
- фильтрацию очереди по состоянию, исходу и подстроке;
- группировку по субъекту и по объекту;
- выбор нескольких изменений и массовое решение по ним;
- вкладку истории решений;
- две темы оформления с переключателем;
- рисунок только по тем связям, которые объясняют оценку.

Модуль **не** делает:

- **правил подавления** вида «всегда игнорировать самовыдачи этого пользователя».
  Система не должна молча прятать изменения от аналитика: раздел «Текущее
  состояние» CLAUDE.md требует, чтобы она не выносила вердикт, а правило подавления
  — это вердикт, принятый заранее и применённый без ведома человека. Повторяющийся
  законный случай закрывается массовым решением, и это каждый раз явный акт;
- аутентификации и разделения пользователей. Аналитик один; поле для его имени в
  схеме есть, но заполняется постоянным значением;
- выгрузки отчётов, уведомлений, живого обновления без запроса.

## 3. Правило, нарушение которого обесценило бы работу

**Решения аналитика никогда не попадают в обучение и ни в какой форме не влияют на
модель.** Ни как метки, ни как веса, ни как фильтр обучающей выборки. Хранилище
триажа читается только слоем HTTP при отдаче очереди и истории.

Обоснование то же, что у раздела 7.3 дизайн-документа: любой путь, по которому
суждение человека об аномальности возвращается в модель, превращает измеренные
числа в самоподтверждение. Ограничение проверяется тестом: модуль `rga.nn` и модуль
`rga.features` не импортируют `rga.service.triage`.

## 4. Архитектура

Рассмотрены три варианта.

**A. Отдельное хранилище, стыкуемое при чтении — выбран.** `analysis.py` остаётся
чистым: строит окно, считает оценки, ранжирует. `triage.py` знает про решения и не
знает про скоринг. Слой HTTP соединяет их при отдаче. Обе части тестируются
порознь, детектор остаётся переносимым и про базу не подозревает.

**B. Состояние внутри анализа.** Анализ сам читает решения и фильтрует очередь.
Меньше движущихся частей, но детектор начинает зависеть от базы, что противоречит
правилу переносимости: выше слоя адаптеров ни один модуль не знает про хранилища.

**C. Состояние в браузере.** Ничего не нужно ставить, но история не переживает
смену браузера, не проверяема и недоступна второму человеку. Противоречит
требованию журнала решений.

## 5. Хранилище

SQLite через стандартный `sqlite3`. Ни одной новой зависимости, файл переносится
копированием, работает одинаково на обеих платформах.

Журнал **только на дозапись**: решение не правится и не удаляется, новое решение
добавляет строку. Текущее состояние инцидента — последняя строка по нему.

```sql
CREATE TABLE IF NOT EXISTS decisions (
    seq        INTEGER PRIMARY KEY AUTOINCREMENT,
    incident   TEXT    NOT NULL,
    outcome    TEXT    NOT NULL,
    note       TEXT    NOT NULL DEFAULT '',
    analyst    TEXT    NOT NULL DEFAULT 'analyst',
    decided_at TEXT    NOT NULL,
    subject    TEXT    NOT NULL,
    relation   TEXT    NOT NULL,
    object     TEXT    NOT NULL,
    score      REAL    NOT NULL
);
CREATE INDEX IF NOT EXISTS decisions_incident ON decisions (incident);
CREATE INDEX IF NOT EXISTS decisions_seq ON decisions (seq DESC);
```

Допустимые значения `outcome`:

| Значение | Что означает | Уходит из очереди |
|---|---|---|
| `confirmed` | подтверждено, требует вмешательства | да |
| `false_positive` | ложное срабатывание | да |
| `accepted_risk` | законно, риск принят | да |
| `reopened` | решение отменено, случай снова в работе | нет |

**Почему субъект, отношение, объект и оценка дублируются в строке решения.** Окно
оценки движется, источник может смениться, инцидент может исчезнуть из текущего
анализа. История обязана оставаться читаемой и тогда: запись решения самодостаточна
и не требует, чтобы инцидент всё ещё существовал.

Идентификатор инцидента — уже существующий `incident_id(key, ts)`, хеш от ключа
ребра и метки времени. Он устойчив к пересчёту анализа: тот же генератор с тем же
сидом даёт те же изменения и те же идентификаторы.

Путь к файлу задаётся в конфигурации сервиса полем `store`, по умолчанию
`var/triage-<имя конфигурации>.db`. Разные демонстрации не делят состояние.

## 6. Интерфейс модуля хранилища

```python
@dataclass(frozen=True)
class Decision:
    """One recorded judgement about one change."""
    seq: int
    incident: str
    outcome: str
    note: str
    analyst: str
    decided_at: str
    subject: str
    relation: str
    object: str
    score: float

class TriageStore:
    def __init__(self, path: Path) -> None: ...
    def record(self, entries: Sequence[Decision]) -> None: ...
    def current(self) -> dict[str, Decision]: ...
    def history(self, *, incident: str | None = None, limit: int = 200) -> tuple[Decision, ...]: ...
    def close(self) -> None: ...
```

`current()` отдаёт последнее решение по каждому инциденту, включая `reopened`.
Очередь считает открытым тот инцидент, по которому решения нет или последнее —
`reopened`.

## 7. HTTP

Существующие ручки сохраняются. Добавляются и расширяются:

```
GET  /api/incidents
        state=open|resolved|all      по умолчанию open
        q=<подстрока>                по субъекту, объекту и инициатору
        outcome=<значение>           только при state=resolved|all
        group=none|subject|object    по умолчанию none
     -> {"incidents": [...], "total": N, "open": N, "resolved": N,
         "groups": [{"key": "...", "count": N, "top_score": X}]}

POST /api/decisions
     {"incidents": ["id", ...], "outcome": "...", "note": "..."}
     -> {"recorded": N, "unknown": ["id", ...]}

GET  /api/decisions?limit=200        история, новые сверху
     -> {"decisions": [...]}

GET  /api/incidents/{id}             существующее + "decision" и "history"
```

Каждый элемент очереди получает поле `state` (`open` или значение исхода) и, если
решение есть, `decided_at`.

Ошибки: неизвестный `outcome` — 422; пустой список инцидентов — 422; инцидент, не
существующий в текущем окне — записывается всё равно, потому что решение
самодостаточно, но в ответе перечисляется в `"unknown"`.

## 8. Страница

Три области, плотная вёрстка в духе Kibana, светлая тема по умолчанию и тёмная по
переключателю. Выбор темы хранится в `localStorage`, никакой другой клиентской
памяти нет.

**Шапка.** Источник, уровень возможностей, имя скорера, время последнего обновления,
кнопка обновления, переключатель темы, вкладки «Очередь» и «История».

**Панель фильтров.** Поиск подстрокой; состояние; исход; группировка. Счётчики
открытых и разобранных рядом.

**Список.** Колонки: чекбокс, ранг, оценка, время, субъект, отношение и уровень,
объект, состояние. В режиме группировки — сворачиваемые группы, в заголовке ключ,
число изменений, наибольшая оценка и кнопка «разобрать группу».

**Панель решения** появляется при выделении хотя бы одного: «выбрано N», три
кнопки исхода, поле заметки, подтверждение.

**Карточка.** Нынешнее содержимое (факты, наблюдения, вклад признаков, связи) плюс
блок текущего решения и история решений по этому инциденту.

**Вкладка «История».** Все записи журнала, новые сверху: время, исход, заметка,
субъект, отношение, объект, оценка на момент решения.

## 9. Рисунок

Сейчас `_subgraph` рисует всю двухшаговую окрестность с ограничением в 60 рёбер, и
это источник нечитаемости: проблема в количестве, а не в раскладке.

Новое правило: рисуются **не больше шести рёбер с наибольшим модулем вклада** плюс
само оцениваемое изменение, если оно уже есть в графе. `edge_importance` продолжает
считать всю окрестность — таблица вкладов её показывает, — но в рисунок попадает
только верхушка. Дорожки остаются жёсткими: user, group, bucket, object слева
направо; барицентровый проход сохраняется.

Тест закрепляет: нарисованных рёбер не больше семи, и каждое входит в верхушку по
модулю вклада.

## 11. Проверка

- Журнал: запись и чтение; последнее решение выигрывает; `reopened` возвращает в
  очередь; история по инциденту в порядке убывания; запись переживает закрытие и
  повторное открытие файла.
- Очередь: `state=open` скрывает решённое; `state=resolved` показывает только его;
  поиск находит по субъекту, объекту и инициатору; группировка даёт правильные
  счётчики; массовое решение записывает по строке на инцидент.
- Разделение слоёв: `rga.nn` и `rga.features` не импортируют `rga.service`.
- Рисунок: не больше семи рёбер, все из верхушки.
- Страница: отдаётся, содержит панель фильтров и переключатель темы.

## 12. Риски

**Состояние и пересчёт расходятся.** Если идентификатор инцидента перестанет быть
устойчивым, решения «отвалятся» от изменений. Закрывается тестом на устойчивость
`incident_id` и тем, что запись решения самодостаточна.

**Разросшийся интерфейс.** Соблазн добавить правила, роли и уведомления. Границы
раздела 2 — часть спецификации, а не пожелание.

**Демонстрация на проекторе.** Тёмная тема на ярком проекторе теряет контраст,
поэтому по умолчанию светлая, а тёмная — по переключателю.
